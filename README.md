# Feature store contracts, synthetic store experiments

Artifact for the EDBT 2027 vision paper *Treat the Feature Store Like the
Database It Is* (Sachidananda Singh). Everything in Section 4 of the paper,
Figure 2, Table 2 and Table 3, is regenerated by one command.

```
pip install -r requirements.txt
python run.py            # about 40 seconds on one machine
python run.py --quick    # 8 seconds, smaller stores, for a smoke test
```

Outputs land in `results/`. The committed `results/` folder is the run the
paper quotes, seed 7.

| File | What it is |
|---|---|
| `results/summary.md` | every number in Section 4, in one place |
| `results/main_reads.csv` | Table 2, three reads on the 300,000 order store |
| `results/sweep_late.csv`, `results/sweep_correction.csv` | Figure 2 data |
| `results/fig_leakage.pdf` | Figure 2 |
| `results/control_no_lag_no_correction.csv` | the control, valid time and bitemporal coincide |
| `results/admission.csv` | Table 3, seven job variants through the admission check |
| `results/cost.csv` | storage in Parquet and median query time per read |
| `results/reach_report.md`, `results/reach_report.json` | the worked deletion reach report |

## What is in the package

`fscontracts/generate.py` builds the store. Forty facilities, thirty open from
day one and ten opening during the two year window. A capacity dimension and a
region to facility assignment dimension, both bitemporal. Every dimension row
carries `valid_from` (the day the fact became true) and `recorded_at` (the day
the store learned it). Recording lag and correction rates are parameters of
`Params`. The fact table is 300,000 orders with a date, a region and a customer.

`fscontracts/reads.py` holds the three training reads as DuckDB SQL. They
differ only in the temporal predicates on the two dimension joins.

- `current`, no predicate, the latest row per key
- `valid`, `valid_from <= order_date`
- `bitemporal`, `valid_from <= order_date AND recorded_at <= order_date`

The bitemporal read is the ground truth for the interpretation "reconstruct
what was known at the decision". The valid time read is the correct read for
the other interpretation, "train on corrected history". A row is leaked when a
read gives it a different facility or capacity from the bitemporal read.

`fscontracts/admission.py` holds the admission check and the seven job
variants. The check reads each job's declaration and never its SQL, which is
both the proposal and its stated limit. J4 declares the right predicates and
implements one with a strict inequality, so it passes and leaks. J6 declares
the corrected history interpretation consistently for a question that needed
the other one, so it passes, because the check cannot know the business
question.

`fscontracts/reach.py` materialises three dataset versions with manifests, a
region week aggregate and three model identifiers, then produces the reach
report for one customer with each hop labelled `tracked`, `consumed`,
`recorded` or `unknown`. No model is trained.

## What this artifact does not show

The store is synthetic. Its lag and correction rates are parameters, so the
leakage numbers are properties of the generator and the read semantics, not of
any production system. The seven job variants were written by the author. The
cost numbers are at toy scale, under 10 KB of dimension history. The paper says
all of this in Section 4 and lists the next stage in Section 6.

## Environment of the committed run

Python 3, DuckDB 1.5.5, pandas 3.0.2, numpy 2.4.4, matplotlib 3.10.9, on one
Linux machine, 2026-09-25. Query times in `results/cost.csv` are medians of
five runs on that machine and will differ elsewhere.
